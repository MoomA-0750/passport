# Passport の暗号設計と脅威モデル

このファイルは「なぜこうなっているか」を残すためのもの。実装を変えるときは先にここを読む。

## 前提

- 完全オフラインの RHEL 10 サーバー。npm から何も取れない。
- 使えるのは **Node.js v20.19.2 の標準ライブラリだけ**。`node_modules` は使わない（→ readme.md「材料」）。
- 通信は自己署名証明書の HTTPS。
- サーバーの管理者は利用者本人（＝あなた）。

## 決めた脅威モデル

**守る:**

| 脅威 | 対策 |
|---|---|
| `data/` ディレクトリのコピーが流出する | パスワード本体は AES-256-GCM 暗号文でしか置かない。マスターキーは `data/` の外 |
| バックアップの tar.gz が流出する | バックアップに マスターキーを含めない。復号には別途キーが必要 |
| ディスクごと持ち去られる（停止中のサーバー） | マスターキーはファイルモード 0400 の別ディレクトリ。パスフレーズ運用なら停止中は鍵が存在しない |
| 他の利用者が、権限のない Vault を覗く | サーバー側の ACL。Vault 単位で owner / editor / viewer（人ごと、またはグループごと。下の「グループと管理者の線引き」） |
| ネットワーク上の盗聴 | HTTPS |
| 暗号文の差し替え・切り貼り | AES-GCM の AAD に `vaultId\|itemId\|field\|version` を入れる（下の「`data/` を書き換えられる人」も読む） |
| ログイン試行の総当たり | scrypt + 「ユーザー名 × 接続元」単位の失敗回数制限 + 接続元単位の総量制限（下を読む） |
| ログの取り違え・後からの否認 | 追記専用の監査ログ（JSONL） |

**守らない（明示的に受け入れるリスク）:**

| 受け入れる脅威 | 理由 |
|---|---|
| **稼働中サーバーの root / プロセスメモリを読める人は、全部読める** | マスターキーが常駐している。管理者＝本人なので、本人を信頼する前提に立った（2026-09-16 の決定） |
| アイテムの **タイトル・ユーザー名・URL・タグは平文** | 一覧と検索を成立させるため。「どのサイトのアカウントを持っているか」は漏れる。秘密そのもの（パスワード / TOTP / セキュアメモ / SSH 秘密鍵 / カスタムフィールド）は必ず暗号化 |
| SSH の **公開鍵とフィンガープリントは平文** | 公開鍵はそもそも公開してよいもの。一覧で見比べたり authorized_keys へ貼るのに毎回復号したくない。秘密鍵とパスフレーズは暗号化する |
| サーバーはログイン時に平文パスワードを受け取る | E2E ではないため。HTTPS と、受け取り後すぐ捨てることで緩和 |

1Password 本体との決定的な違いはここ。1Password は「サーバーは何も知らない」が出発点だが、Passport は
「サーバーは知っているが、盗まれたファイルは何も語らない」を狙う。1人の管理者が運用する社内ツールとしては、
実装量と運用の現実性を取ってこちらを選んだ。

## `data/` を書き換えられる人について（2026-09-16 に線引きを決めた）

上の「守る」表は `data/` の**流出（読み取り）**しか挙げていないのに、AAD は**書き換え対策**として
作ってある。範囲が曖昧だったので、ここで決める。

**結論: 書き換えられる人も脅威として扱う。ただし「防ぎきる」とは言わない。**

理由: `data/` を書き換えられる人は、たいていサーバーの root を取れている（＝受け入れ済みの
「稼働中サーバーの root は全部読める」と地続き）。それでも、バックアップ領域への書き込み権限だけを持つ、
復元作業で古いファイルを混ぜてしまう、といった**root 未満でも起こる経路**があるので、
安く防げるものは防いでおく。

### 防げるもの

| 書き換え | どうなるか |
|---|---|
| 別 Vault・別アイテム・別フィールドの暗号文を貼り付ける | AAD が合わず復号に失敗する |
| 同じフィールドの古い世代の暗号文へ戻す | AAD の世代が合わず復号に失敗する（ただし下の注意を読む） |
| ユーザーの権限を書き換える（`vault.json` の members / groups、`data/groups/` の members を含む） | 防げない。ただし監査ログとの食い違いで気づける |

### 防げないもの（受け入れる）

| 書き換え | なぜ防げないか |
|---|---|
| **アイテムのファイルを、古い世代へ丸ごと戻す** | ファイル内のどんな印も一緒に巻き戻るので、**外部の単調カウンタなしには原理的に検出できない**。古いパスワードが正規の値として見える |
| **秘密を削除して入れ直すと、世代番号が 1 に戻る** | 世代はフィールドのレコードに載っているため、消せばカウンタも消える。初代の暗号文を貼り戻せる（再現済み）。削除後もカウンタを残す実装にすれば塞げるが、ファイル丸ごとの巻き戻しは残るので、決定的な対策にはならない |
| `data/users/` を消して、セットアップ画面を復活させる | **これは防ぐ**（下の「起動時に確かめること」参照）。ファイルが読めない場合も含めて、セットアップは開かない |

### 例外: オートフィルの宛先だけは完全性を守る

アイテムの `urls` は平文で、Chrome 拡張はこれを見て「このサイトで使える候補」を決める。
ここを書き換えられると、**本物のパスワードが攻撃者のホストへ入力される**。
ほかの書き換え被害（古い値が見える、権限が変わる）とは質が違うので、ここだけは完全性を守る。

```
urlsMac = HMAC-SHA256(
  key  = HKDF(vaultKey, salt=itemId, info="passport/item-urls-mac/v1"),
  data = JSON({ vaultId, itemId, urls })
)
```

- 鍵は Vault 鍵から導くので、`data/` だけを持っている人には作れない
- `vaultId` と `itemId` も縛るので、別のアイテムの正しい印を貼り替えても通らない
- 合わないアイテムは、ホストが一致してもオートフィルの候補から外し、監査ログに `tampered` として残す

**移行は一度だけ。** この仕組みを入れる前のアイテムには印が無いので、起動時に付けて回る。
ただし「起動のたびに、無いものには付ける」にすると、攻撃者は印を消して `urls` を書き換え、
再起動を待つだけで改ざんを正規扱いにできる。そこで移行が済んだことを `keycheck.json` に記録し、
以後は「印が無い＝改ざん」とみなす。

## グループと管理者の線引き（2026-09-16）

グループは暗号ではなく ACL の話だが、「管理者が Vault の中を見られるか」を変えるのでここに置く。

- 実効ロールは、個人に付いたロールと所属グループのロールのうち最強のもの。判定は `vaults.roleOf` の1か所だけ。
  キャッシュしないので、グループから外せばその場で効く
- Vault Key はグループごとに包み直さない。サーバー側暗号なので、権限の判定だけで足りる
  （E2E に移すときは、グループ用の鍵ペアを作って `wrappedKeys` に足すことになる）
- **管理者はグループの中身を変えられるので、Vault の owner の同意なしに人を Vault に入れられる。**
  これはグループという仕組みの前提として受け入れる（owner は、グループを共有先に足した時点で
  「中身は管理者が決める」ことに同意している）。owner には共有画面でグループの中の人が見える
- **グループに付けられるのは viewer / editor だけ。owner は人にだけ付く**（Fable のレビューで決めた）。
  グループに owner を付けられると、管理者がグループに入れた人が、自分を個人の owner に足して
  元の owner を外せる。つまり管理者が緊急アクセスを通らずに Vault の支配権を配れてしまう。
  ファイルに owner と書かれていても `roleOf` は editor として扱う
- この決まりで「実効 owner ＝ 個人で入っている owner」が常に成り立つ。後から作る機能
  （自分の履歴で他人の操作を見せる範囲、自動化トークンの発行者）は、これに乗ってよい
- **管理者が自分自身をグループに入れることはできない。** 入れられると、理由必須の緊急アクセス
  （`break_glass`）を通らずに Vault の中を見られてしまう。入れたときの監査ログには、
  その人が見られるようになった Vault の名前を残す
- ただしこれは**うっかりを防ぐガードレールで、境界ではない**。管理者は、ユーザーを作ってそのユーザーを入れる、
  パスワードをリセットしてなりすます（グループ以前からある経路）、別の管理者と入れ合う、で迂回できる。
  「管理者＝運用者本人を信頼する」前提（上の表）の中で受け入れる。どの経路も監査ログには残る
- 無効化中のユーザーはグループに入れられない（有効化した瞬間に、グループの記録なしで入れるようになるため）
- 最後の owner の保護は、書き込む直前の内容に対して、個人で入っている owner を数える

## 将来 E2E に移す余地

Vault 鍵の包み方を、最初からデータ構造として外に出しておく。

```json
"wrappedKeys": [
  { "holder": "server", "method": "server-kek-v1", "envelope": { ... } }
]
```

E2E に移すときは、`holder` をユーザーIDに、`method` を `user-x25519-v1` にした要素を足していく。
Node 標準 crypto は X25519 の ECDH を持っているので、材料を増やさずに移行できる。
今それを作らないだけで、道は塞いでいない。

## 鍵階層

```
マスターキー（32バイト）
│   ・キーファイル /etc/passport/master.key （既定。0400。systemd で自動起動できる）
│   ・または環境変数 PASSPORT_MASTER_PASSPHRASE から scrypt で導出（起動ごとに人手アンロック）
│
├─ KEK = HKDF-SHA256(masterKey, info="passport/kek/v1")
│   │
│   └─ Vault Key（Vault ごとに 32バイトのランダム）
│       ・KEK で AES-256-GCM 暗号化して vault.json に保存
│       │
│       └─ Item Key = HKDF-SHA256(vaultKey, salt=itemId, info="passport/item/v1")
│           ・秘密フィールドごとに AES-256-GCM
│           ・AAD = "vaultId|itemId|fieldName|version"
│
└─ AUTH_PEPPER = HKDF-SHA256(masterKey, info="passport/pepper/v1")
    ・パスワードハッシュに混ぜる。DB だけ盗まれてもオフライン総当たりができない
```

**なぜ Item Key を分けるか**: 同一鍵での GCM 暗号化回数を抑えるため、そして AAD で
「別アイテムの暗号文を貼り付ける」攻撃を落とすため。HKDF は速いのでコストはない。

## 封筒フォーマット

暗号文は必ずこの形の JSON で保存する。将来アルゴリズムを変えても読めるように `v` と `alg` を持つ。

```json
{ "v": 1, "alg": "A256GCM", "iv": "<base64 12バイト>", "ct": "<base64>", "tag": "<base64 16バイト>" }
```

## パスワードハッシュ

```
scrypt(password + AUTH_PEPPER, salt=16バイトランダム, N=2^15, r=8, p=1, dkLen=32, maxmem=64MiB)
```

- `maxmem` を明示しないと Node の既定 32MiB を超えて落ちる（必要量 = 128 * N * r = 33.5MiB）。**消さないこと。**
- 比較は必ず `crypto.timingSafeEqual`。
- パラメータはハッシュと一緒に保存する。将来上げるときは、ログイン成功時に静かに再ハッシュする。

## やらないと決めたこと

- 自前のアルゴリズム実装（AES も HMAC も Node 標準を使う。JS で書き直さない）
- `node_modules` からの暗号ライブラリ抽出（標準で足りるものを増やす理由がない）
- パスワードの「復号できるヒント」機能。マスターキーを失ったら復号不可。その前提で運用手順を書く


## SSH 鍵について

秘密鍵（`privateKey`）とパスフレーズ（`passphrase`）は、ほかの秘密と同じ封筒に入れる。
AAD も同じ決まりなので、別アイテムの鍵を貼り替えても復号できない。

**生成した鍵にパスフレーズは掛けていない。** OpenSSH 形式でパスフレーズを掛けるには
bcrypt_pbkdf（Blowfish）が要り、標準ライブラリだけで書くには重すぎる。
Passport 側が保管時に暗号化しているので、保管の観点では二重に掛ける必要はない。
取り出してファイルに置いたあとも掛けたい場合は `ssh-keygen -p -f <ファイル>` を案内する。

**パスフレーズ付きの鍵を預かるときは、パスフレーズを渡さなくても登録できる。**
OpenSSH 形式は暗号化されていても公開鍵の部分が平文なので、
そこから鍵種別・公開鍵・フィンガープリントが取れる。
中身を開く必要がないので、bcrypt_pbkdf を実装しないで済んでいる。

## Chrome 拡張の認証

拡張は Cookie ではなく `Authorization: Bearer <トークン>` を使う。トークンの実体はセッションIDそのもの。

**なぜ Cookie にしないか。** サーバーは拡張からの呼び出しに CSRF 検証をしない
（拡張の Origin からは CSRF トークンを載せられないため）。
ここで Cookie も受け付けると、「金庫にログイン中のブラウザで開いた別サイトから、
Cookie が勝手に付いた状態で API を叩ける」経路ができる。
Bearer は勝手には付かないので、この経路が生まれない。

そのため実装では、**Cookie で認証したリクエストには必ず CSRF 検証を通し、
Bearer のときだけ省く**。「Bearer ヘッダーがあれば素通し」にはしない（あると素通しにすると、
攻撃者が空の Bearer を付けるだけで検証を外せてしまう）。

ほかに効かせていること:

- トークンを返すのは、許可した拡張 ID の Origin から来たログインだけ。画面には返さない
  （画面は HttpOnly Cookie で動いているので、JS から読めるトークンを渡すとその守りを外すことになる）
- CORS の `Access-Control-Allow-Origin` は許可した拡張 ID にだけ返す。
  `Allow-Credentials` は付けない（Cookie を伴う越境リクエストを許さない）
- 拡張側はトークンを `chrome.storage.session` に置く。ブラウザを閉じれば消える。
  `local` に置くとディスクに残るので置かない


## 入力欄のそばのメニュー（content script）

ページの中で動くので、拡張のほかの部分より近いところに置かれる。効かせていること:

- **既定では動かない。** 本人が許可した origin にだけ `registerContentScripts` で登録する
- メニューは **closed な Shadow DOM**。ページ側の JS から `shadowRoot` を辿れず、中の要素を掴めない。
  **ただし CSS には干渉される。** `closed` が守るのは JS からの到達だけで、
  ホスト要素はページのツリーにいる普通の div なので、ページの `!important` で
  透明化も移動もできる（実際に再現した）。そこで次の2枚を足した:
  - ホスト要素の危ない性質を、インラインの `!important` で毎回押さえ直す
    （インラインの `!important` はページの `!important` より強い）
  - 埋める直前に、祖先まで遡った実効的な不透明度と `elementFromPoint` を確かめる
    （ページは祖先を薄くすることでも隠せるため）
- 埋めるのは **`isTrusted` なクリックのときだけ**。ページが合成イベントを投げても動かない
- **メニューを開くのは、直前に本物の操作があったときだけ。**
  ページが `element.focus()` を呼んで出る focusin は `isTrusted === true` になるので、
  `isTrusted` だけでは「ページが勝手に開く」を止められない
- **候補を出す対象は sender の origin から決める。** content script が
  「このホストの分をくれ」と指定する形にはしていない。ページが content script の
  メッセージを偽装できたとしても、別サイトの資格情報は出てこない
- 入力を頼まれたときも、background 側でそのアイテムがそのホストの候補に含まれるかを確かめる
- content script は秘密を保持しない。埋める瞬間に受け取り、欄に入れたら忘れる

残っているリスク: 埋めたあとの値は、そのページの JavaScript から読める。
これはオートフィルという仕組みそのものの性質で、ホストの照合を厳しくすること以上の対策はない。


## ログインを捉えてから保存するまでの預かり

「保存しますか」を出すには、ページが遷移して消えたあとも入力された値を持っている必要がある。
ここは、この拡張が**平文のパスワードを一時的に保持する唯一の場所**なので、条件を絞ってある。

置き場は `chrome.storage.session`。ディスクには書かれず、ブラウザを閉じれば消える。
`local` には置かない。

そのうえで、

- **2分の期限**を付ける。過ぎたものは次に触ったときに捨てる
- 保存か却下が決まった時点で消す
- タブを閉じたら、そのタブの分を消す
- **金庫をロックしたら全部消す**
- 捉えたのと同じホストにいるときしか提案しない。
  別のサイトへ遷移した先で、よそのパスワードの保存を勧めない

content script 側には残さない。捉えたらすぐ background へ渡し、
バーに出すのもホストとユーザー名までで、パスワードは出さない。

受け入れているリスク: この2分の間、ブラウザのメモリ上に平文が存在する。
提案そのものを諦めない限り避けられないので、期限と消去のきっかけを増やすことで抑えている。
機能ごと切ることもできる（設定画面のトグル）。


## 保管してある値との照合（/verify）

「このログインはもう登録済みか」を判断するのに、保管してある平文を拡張へ渡す必要はない。
そこで、サーバー側で照合だけして真偽を返す口を用意した。

- 比較は `crypto.timingSafeEqual`。長さが違う場合は先に落とす
- 必要な権限は閲覧と同じ（viewer 以上）。
  呼ぶ側は候補の値を既に持っており、その気になれば `/reveal` で平文を取れる立場なので、
  ここで真偽を返しても新しく与えるものはない
- 監査ログには `item.verify_secret` として、`match` / `differs` の別とともに残す。
  `item.view_secret`（閲覧）とは分けてあるので、「誰が実際に中身を見たか」の記録が薄まらない


## ログイン試行の制限（2026-09-16 に作り直した）

以前は「ユーザー単位で5回失敗したら、**正しいパスワードでも**15分入れない」だった。
これだと、ユーザー名さえ知っていれば誰でも特定の人を締め出せる。15分ごとに5回デタラメを送り続ければ
永久に入れず、最後の管理者を狙われると誰もリセットできない（レビューで指摘）。

今の数え方（`lib/throttle.js`）:

- **「ユーザー名 × 接続元 IP」の組み合わせ**で数える。攻撃者が自分の IP から失敗を重ねても、
  別の場所から正しく入る本人には効かない
- **存在しないユーザー名でも同じように数える。** 以前は存在しないユーザー名は止められなかったので、
  「429 が返るか」で実在するユーザーを機械的に選別できた
- 接続元 IP 単位でも、ユーザー名をまたいだ総量を抑える（15分に30回）。scrypt でサーバーが止まるのを防ぐ
- どの失敗でも、利用者への応答（ステータスと文言）と所要時間をそろえる。
  無効化されたユーザー・止められた組み合わせでも、形だけの scrypt を回す

**受け入れていること:** 多数の IP から1人を狙う分散型の総当たりは、この仕組みだけでは止まらない。
scrypt の計算コスト、パスワードの最低12文字、監査ログでの検知で抑える。
締め出し攻撃（1つの IP から誰でもできる）と比べて、社内ネットワークでは起こりにくいと判断した。

## セッションの寿命

- 操作があるたびに有効期限（既定8時間）を延ばす
- ただし**ログインから一定時間（既定24時間）を越えたら、操作が続いていても切る。**
  以前は延長に上限が無く、8時間おきに1回叩き続ければ、拡張の Bearer トークンを含めて無期限に生きていた

## CSRF の免除

Chrome 拡張からの呼び出しは CSRF 検証を省く。免除の条件は
「**Bearer トークンが、実在するセッションに解決できたとき**」だけ。
以前は Authorization ヘッダーの形だけで免除していたので、でたらめな Bearer を付ければ Origin もトークンも見られなかった
（ブラウザからは preflight で止まるため到達できず実害は無かったが、外から自由に作れる条件に乗っていた）。
