# Passport の暗号設計と脅威モデル

このファイルは「なぜこうなっているか」を残すためのもの。実装を変えるときは先にここを読む。

## 前提

- 完全オフラインの RHEL 10 サーバー。npm から何も取れない。
- 使えるのは **Node.js v20.19.2 の標準ライブラリだけ**。`node_modules` は使わない（→ readme.md「材料」）。
- 通信は自己署名証明書の HTTPS。
- サーバーの管理者は利用者本人（＝あなた）。

## 決めた脅威モデル

**守る:**

| 脅威 | 対策 |
|---|---|
| `data/` ディレクトリのコピーが流出する | パスワード本体は AES-256-GCM 暗号文でしか置かない。マスターキーは `data/` の外 |
| バックアップの tar.gz が流出する | バックアップに マスターキーを含めない。復号には別途キーが必要 |
| ディスクごと持ち去られる（停止中のサーバー） | マスターキーはファイルモード 0400 の別ディレクトリ。パスフレーズ運用なら停止中は鍵が存在しない |
| 他の利用者が、権限のない Vault を覗く | サーバー側の ACL。Vault 単位で owner / editor / viewer |
| ネットワーク上の盗聴 | HTTPS |
| 暗号文の差し替え・切り貼り | AES-GCM の AAD に `vaultId\|itemId\|field\|version` を入れる |
| ログイン試行の総当たり | scrypt + 失敗回数ロック |
| ログの取り違え・後からの否認 | 追記専用の監査ログ（JSONL） |

**守らない（明示的に受け入れるリスク）:**

| 受け入れる脅威 | 理由 |
|---|---|
| **稼働中サーバーの root / プロセスメモリを読める人は、全部読める** | マスターキーが常駐している。管理者＝本人なので、本人を信頼する前提に立った（2026-09-16 の決定） |
| アイテムの **タイトル・ユーザー名・URL・タグは平文** | 一覧と検索を成立させるため。「どのサイトのアカウントを持っているか」は漏れる。秘密そのもの（パスワード / TOTP / セキュアメモ / SSH 秘密鍵 / カスタムフィールド）は必ず暗号化 |
| SSH の **公開鍵とフィンガープリントは平文** | 公開鍵はそもそも公開してよいもの。一覧で見比べたり authorized_keys へ貼るのに毎回復号したくない。秘密鍵とパスフレーズは暗号化する |
| サーバーはログイン時に平文パスワードを受け取る | E2E ではないため。HTTPS と、受け取り後すぐ捨てることで緩和 |

1Password 本体との決定的な違いはここ。1Password は「サーバーは何も知らない」が出発点だが、Passport は
「サーバーは知っているが、盗まれたファイルは何も語らない」を狙う。1人の管理者が運用する社内ツールとしては、
実装量と運用の現実性を取ってこちらを選んだ。

## 将来 E2E に移す余地

Vault 鍵の包み方を、最初からデータ構造として外に出しておく。

```json
"wrappedKeys": [
  { "holder": "server", "method": "server-kek-v1", "envelope": { ... } }
]
```

E2E に移すときは、`holder` をユーザーIDに、`method` を `user-x25519-v1` にした要素を足していく。
Node 標準 crypto は X25519 の ECDH を持っているので、材料を増やさずに移行できる。
今それを作らないだけで、道は塞いでいない。

## 鍵階層

```
マスターキー（32バイト）
│   ・キーファイル /etc/passport/master.key （既定。0400。systemd で自動起動できる）
│   ・または環境変数 PASSPORT_MASTER_PASSPHRASE から scrypt で導出（起動ごとに人手アンロック）
│
├─ KEK = HKDF-SHA256(masterKey, info="passport/kek/v1")
│   │
│   └─ Vault Key（Vault ごとに 32バイトのランダム）
│       ・KEK で AES-256-GCM 暗号化して vault.json に保存
│       │
│       └─ Item Key = HKDF-SHA256(vaultKey, salt=itemId, info="passport/item/v1")
│           ・秘密フィールドごとに AES-256-GCM
│           ・AAD = "vaultId|itemId|fieldName|version"
│
└─ AUTH_PEPPER = HKDF-SHA256(masterKey, info="passport/pepper/v1")
    ・パスワードハッシュに混ぜる。DB だけ盗まれてもオフライン総当たりができない
```

**なぜ Item Key を分けるか**: 同一鍵での GCM 暗号化回数を抑えるため、そして AAD で
「別アイテムの暗号文を貼り付ける」攻撃を落とすため。HKDF は速いのでコストはない。

## 封筒フォーマット

暗号文は必ずこの形の JSON で保存する。将来アルゴリズムを変えても読めるように `v` と `alg` を持つ。

```json
{ "v": 1, "alg": "A256GCM", "iv": "<base64 12バイト>", "ct": "<base64>", "tag": "<base64 16バイト>" }
```

## パスワードハッシュ

```
scrypt(password + AUTH_PEPPER, salt=16バイトランダム, N=2^15, r=8, p=1, dkLen=32, maxmem=64MiB)
```

- `maxmem` を明示しないと Node の既定 32MiB を超えて落ちる（必要量 = 128 * N * r = 33.5MiB）。**消さないこと。**
- 比較は必ず `crypto.timingSafeEqual`。
- パラメータはハッシュと一緒に保存する。将来上げるときは、ログイン成功時に静かに再ハッシュする。

## やらないと決めたこと

- 自前のアルゴリズム実装（AES も HMAC も Node 標準を使う。JS で書き直さない）
- `node_modules` からの暗号ライブラリ抽出（標準で足りるものを増やす理由がない）
- パスワードの「復号できるヒント」機能。マスターキーを失ったら復号不可。その前提で運用手順を書く


## SSH 鍵について

秘密鍵（`privateKey`）とパスフレーズ（`passphrase`）は、ほかの秘密と同じ封筒に入れる。
AAD も同じ決まりなので、別アイテムの鍵を貼り替えても復号できない。

**生成した鍵にパスフレーズは掛けていない。** OpenSSH 形式でパスフレーズを掛けるには
bcrypt_pbkdf（Blowfish）が要り、標準ライブラリだけで書くには重すぎる。
Passport 側が保管時に暗号化しているので、保管の観点では二重に掛ける必要はない。
取り出してファイルに置いたあとも掛けたい場合は `ssh-keygen -p -f <ファイル>` を案内する。

**パスフレーズ付きの鍵を預かるときは、パスフレーズを渡さなくても登録できる。**
OpenSSH 形式は暗号化されていても公開鍵の部分が平文なので、
そこから鍵種別・公開鍵・フィンガープリントが取れる。
中身を開く必要がないので、bcrypt_pbkdf を実装しないで済んでいる。

## Chrome 拡張の認証

拡張は Cookie ではなく `Authorization: Bearer <トークン>` を使う。トークンの実体はセッションIDそのもの。

**なぜ Cookie にしないか。** サーバーは拡張からの呼び出しに CSRF 検証をしない
（拡張の Origin からは CSRF トークンを載せられないため）。
ここで Cookie も受け付けると、「金庫にログイン中のブラウザで開いた別サイトから、
Cookie が勝手に付いた状態で API を叩ける」経路ができる。
Bearer は勝手には付かないので、この経路が生まれない。

そのため実装では、**Cookie で認証したリクエストには必ず CSRF 検証を通し、
Bearer のときだけ省く**。「Bearer ヘッダーがあれば素通し」にはしない（あると素通しにすると、
攻撃者が空の Bearer を付けるだけで検証を外せてしまう）。

ほかに効かせていること:

- トークンを返すのは、許可した拡張 ID の Origin から来たログインだけ。画面には返さない
  （画面は HttpOnly Cookie で動いているので、JS から読めるトークンを渡すとその守りを外すことになる）
- CORS の `Access-Control-Allow-Origin` は許可した拡張 ID にだけ返す。
  `Allow-Credentials` は付けない（Cookie を伴う越境リクエストを許さない）
- 拡張側はトークンを `chrome.storage.session` に置く。ブラウザを閉じれば消える。
  `local` に置くとディスクに残るので置かない


## 入力欄のそばのメニュー（content script）

ページの中で動くので、拡張のほかの部分より近いところに置かれる。効かせていること:

- **既定では動かない。** 本人が許可した origin にだけ `registerContentScripts` で登録する
- メニューは **closed な Shadow DOM**。ページ側の JS から `shadowRoot` を辿れず、
  中の要素を掴めない。ページの CSS にも干渉されない
- 埋めるのは **`isTrusted` なクリックのときだけ**。ページが合成イベントを投げても動かない
- **候補を出す対象は sender の origin から決める。** content script が
  「このホストの分をくれ」と指定する形にはしていない。ページが content script の
  メッセージを偽装できたとしても、別サイトの資格情報は出てこない
- 入力を頼まれたときも、background 側でそのアイテムがそのホストの候補に含まれるかを確かめる
- content script は秘密を保持しない。埋める瞬間に受け取り、欄に入れたら忘れる

残っているリスク: 埋めたあとの値は、そのページの JavaScript から読める。
これはオートフィルという仕組みそのものの性質で、ホストの照合を厳しくすること以上の対策はない。


## ログインを捉えてから保存するまでの預かり

「保存しますか」を出すには、ページが遷移して消えたあとも入力された値を持っている必要がある。
ここは、この拡張が**平文のパスワードを一時的に保持する唯一の場所**なので、条件を絞ってある。

置き場は `chrome.storage.session`。ディスクには書かれず、ブラウザを閉じれば消える。
`local` には置かない。

そのうえで、

- **2分の期限**を付ける。過ぎたものは次に触ったときに捨てる
- 保存か却下が決まった時点で消す
- タブを閉じたら、そのタブの分を消す
- **金庫をロックしたら全部消す**
- 捉えたのと同じホストにいるときしか提案しない。
  別のサイトへ遷移した先で、よそのパスワードの保存を勧めない

content script 側には残さない。捉えたらすぐ background へ渡し、
バーに出すのもホストとユーザー名までで、パスワードは出さない。

受け入れているリスク: この2分の間、ブラウザのメモリ上に平文が存在する。
提案そのものを諦めない限り避けられないので、期限と消去のきっかけを増やすことで抑えている。
機能ごと切ることもできる（設定画面のトグル）。
